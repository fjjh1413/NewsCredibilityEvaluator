# ADR-001：先使用内部确定性状态图拆分检测 Agent

## Status

Accepted

## Date

2026-08-13

## Context

检测服务已经具备 RAG、联网路由、模型仲裁、聚焦重试、降级评分、持久化和 Agent Trace，但这些控制流集中在一个约 337 行、认知复杂度 42 的函数中。P1 需要让节点、条件边和状态转换成为一等工程对象，同时不能破坏 15 个直接调用方、大量基于原模块路径的测试打桩和既有 API 契约。

## Decision

实现一个项目内、无第三方依赖的同步确定性状态图执行器，并用显式 `DetectionAgentState` 承载单次运行状态。节点保持现有服务模块的稳定依赖边界，主函数只负责构建状态和执行图。

图执行器只提供当前需要的能力：普通边、条件边、执行路径、节点状态、耗时、失败记录和最大步数保护。它不提供持久化检查点、分布式调度或动态多 Agent 协作。

## Alternatives considered

### 立即引入 LangGraph

- 优点：成熟的状态图、检查点、中断和生态能力。
- 缺点：当前尚未验证耐久执行或人工中断需求；会同时引入依赖迁移与业务拆分两个变量。
- 结论：P1 拒绝；状态契约稳定后再做运行时对比。

### 继续保留单体函数，仅扩展 Agent Trace

- 优点：改动最小。
- 缺点：轨迹只是事后描述，无法独立验证条件边，也不能降低编排复杂度。
- 结论：拒绝。

### 多模型角色协作

- 优点：演示效果明显。
- 缺点：增加延迟、成本和不确定性；当前流程大多是确定性工具编排，不需要额外模型角色。
- 结论：拒绝。

## Consequences

- 收益：节点与路径可测试；Agent Trace 可以由真实执行路径驱动；未来接入耐久运行时有明确迁移边界。
- 成本：内部执行器需要维护严格的小范围 API；当前仍是进程内同步执行，不支持跨进程恢复。
- 兼容：不改数据库表，不增加模型调用，不删除旧 `agent_steps`，同步与 Celery 调用方继续使用原服务入口。

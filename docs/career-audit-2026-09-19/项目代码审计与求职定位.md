## 2. 真实技术架构与数据流

### 2.1 架构性质

这是一个**模块化单体后端 + 独立worker + Vue前端**。同一套业务代码处理检测与管理，MySQL保存业务真相，Chroma保存可重建检索索引，文件系统保存报告，Redis按配置承担缓存、限流和任务消息。不是企业级微服务架构。[C05]

~~~mermaid
flowchart TD
  U[用户输入标题/正文/可选URL] --> V[Vue DetectView]
  V --> P[可选: URL提取预览]
  P --> V
  V --> A[FastAPI /api/detect/news]
  A --> G[认证可选 + 输入校验 + IP限流]
  G --> M{异步配置}
  M -->|默认同步| D[固定状态图检测流程]
  M -->|开启| T[MySQL DetectionTask]
  T --> Q[Redis / Celery worker]
  Q --> D
  D --> C[清洗 + 规则主张提取]
  C --> E[Query Embedding]
  E --> R[Chroma检索 / 可选v2词项融合]
  R --> K[MySQL知识数据 / v1存在性回查]
  K --> W{本地证据不足且允许联网}
  W -->|是| S[Bocha搜索摘要]
  W -->|否| X[候选证据构造]
  S --> X
  X --> L[主LLM分析]
  L --> J[仲裁校验 + 最多一次focused修复]
  J --> F[有效证据 + 质量调整 + 条件评分]
  F --> DB[MySQL检测/证据/JSON快照]
  DB --> O[API响应 / Vue结果页]
  O --> RP[用户另行请求生成报告]
  RP --> FL[HTML/PDF文件]
  FL --> RD[报告记录及下载地址]
  RD --> DL[鉴权下载/前端展示]
~~~

几个顺序必须纠正：

1. **不是先把每次用户输入入库再Embedding。** 同步路径先检索与分析，最终保存检测；异步路径才会先保存任务。知识库另有写入/索引链路。
2. URL正文提取是独立的预览操作；提交了URL不等于每次检测都会抓全文。检索补网主要使用搜索返回的摘要，不能说每条证据都经过全文核验。
3. 报告在结果页另行生成，不是每次检测的必经阶段。
4. 当前前端提交后只读取 detection_id；异步API返回 task_id/202，但前端没有对应轮询流程。默认同步可走通的设计，不代表开启异步后页面可直接使用。[F01][F02][D02]

### 2.2 知识写入是独立链路

管理员/采集 → MySQL知识条目与索引任务同事务写入 → scheduler消费 → Embedding → Chroma upsert → 更新向量/任务状态。失败按配置重试，超过次数进入dead；删除另有补偿路径。[B02][B03]

这里解决的是**最终一致性**，不是 MySQL 与 Chroma 的原子事务。任务处理缺少跨进程原子抢占和过期processing回收；v2删除旧chunk再upsert也有中间窗口。[R04][B03]

### 2.3 四种存储如何对应

| 存储 | 保存什么 | 关联与风险 |
|---|---|---|
| MySQL | 用户、知识、检测、证据、报告、Prompt、日志、采集/检测/索引任务 | knowledge_id/detection_id/user_id；关系数据为业务主记录 |
| Chroma | v1条目向量或v2 chunk向量与metadata | knowledge_id连接MySQL；v1查回数据库，v2缺少同样复核 |
| 文件 | HTML/PDF报告 | reports的相对路径 + detection.report_url；文件与DB只能补偿 |
| Redis | 缓存、限流计数、Celery消息/结果 | 不是主业务库；当前compose关闭AOF与快照，队列持久性不足 |

检测JSON保存候选、仲裁及状态等快照，但规范化 evidence_matches 写入没有完整传递已有的来源URL、类型、时间字段；PDF上下文也没有完整原文URL引用。可以说“保留证据候选与分析依据”，不能说“全链路完整引用可追溯已闭环”。[D10][B04]

## 3. AI链路、安全与可靠性的深度判断

### 3.1 RAG：实现了什么，尚未证明什么

**默认路径是v1。** 配置代码与 .env.example 都是 RAG_INDEX_VERSION=v1；v2需要显式开启并构建chunk索引。名称为hybrid的索引模式表示“先v2，空结果才回退v1”，不是两套索引结果同时融合。[C01][C02][R01]

| 技术点 | 真实实现 | 状态与边界 |
|---|---|---|
| Chunking | 段落优先、长文滑窗，配置700字符/重叠100；分别构造知识的不同文本片段 | v2已实现；单位是字符，不是token；追加重叠使其不是严格700字符上限 |
| Embedding | 默认DashScope text-embedding-v4、1024维；hash模式服务测试/演示 | 已实现适配；hash没有语义能力；local保留项未实现，其他provider不等于真实服务已验证 |
| Vector Search | Chroma持久化，cosine距离转换为 max(0,1-distance) | v1可解释为余弦相关分；不是事实可信度 |
| 多查询 | 规则抽最多5个主张，最多4路query，各取Top10，再RRF融合 | 已接入；不是LLM自主规划查询 |
| v2混合检索 | dense候选 + SQL词项候选，按父知识ID聚合；RRF或加权融合 | 已实现可配置路径；lexical是字段命中启发式，不是BM25 |
| Metadata filter | v2索引版本及可选类别/标签/风险过滤参数 | 底层支持不等于主检测每次都启用这些筛选 |
| Candidate filtering | v1检索后查MySQL存在性并更新metadata | v2提前返回，没有相同完整复核 |
| 去重 | 本地与网络各自强身份去重；后端对文本近重复做质量惩罚 | 没有跨源统一硬去重；不是语义去重模型 |
| MMR | 函数实际对重复source_name减分 | 不应写“实现标准MMR”，没有向量间novelty计算 |
| Rerank | 相关分、融合分、query命中、spans等规则加权 | 已接入规则重排；model callback未传入，模型reranker只是扩展点 |
| Context construction | 候选ID、确定性中立顺序、证据上限、supporting spans | 已实现；“压缩”仍保留完整document/chunks，未证明节省token |
| Quality control | LLM对候选rank/reject，后端验证ID、覆盖和字段，再生成有效证据 | 是强项；质量仍依赖模型及启发式，未证明实际可靠性 |

对应：[分块][R03]、[Embedding][R12]、[向量索引][R04]、[召回融合][R02]、[多查询][R09]、[重排][R05]、[片段提取][R11]。

**联网条件必须准确表述：** 全局开关与请求允许联网时，无候选会联网；否则取首位分数top1，若top1＜0.45，或top1＜0.60且分数≥0.30的候选少于3条，则联网。只有1条但top1≥0.60时并不会联网。网络搜索失败返回空结果，保留本地分析；本地向量检索异常则会形成失败响应，不是自动转向网络。[R06][D02]

**重要语义缺口：** v2把融合后的final_score放进similarity_score，随后沿用v1的0.45/0.60阈值；融合分与cosine不是同一量纲。规则重排后首条也未必拥有最大的原始similarity。因此不能写“已通过统一相似度阈值保证检索质量”。[R08][R02][R06]

**重要上下文缺口：** 联网补证成功后的merge_evidence重建字典，只保留基础字段，丢弃本地v2的chunks、supporting_spans、index_version、score_components。v2单独检索的测试通过，也不能替代“v2＋联网＋Prompt＋持久化”组合测试。[R07]

### 3.2 LLM：确实是Pipeline，但不是复杂自主Agent

执行步骤为：模板选择与校验 → 清洗/转义 → 系统指令与候选上下文 → 追加统一输出契约 → 主模型调用 → JSON容错解析 → 字段归一化 → 证据语义校验 → 至多一次focused仲裁修复 → 质量调整 → 评分。[D04][D06][D07]

关键设计：

- 主请求明确system/user，temperature=0.2，response_format=json_object，默认HTTP超时30秒。
- 输出契约2.1共享9个顶层字段与4级风险定义；json_object不是供应商侧严格JSON Schema解码。
- 候选ID必须来自输入；ranked/rejected不能重复或交叉，必须覆盖候选；分值、stance和reason经过验证。
- 不合格时只重做证据仲裁，不重跑整条检索；再失败标记retry_exhausted，不把非法排名当有效证据。
- Prompt模板有数据库管理、默认项和校验；**未建立不可变Prompt版本、发布、回滚和效果对比闭环**。
- 有提示注入防御说明、输入转义与输出契约约束；不能声称根除Prompt Injection。
- 为中立排序剥离检索提示字段的逻辑只处理顶层，嵌套chunk分数等仍可能泄漏到Prompt。[D06]

解析器有容错不代表输入类型处理完美：仲裁验证器先list转换再判断list的局部逻辑削弱类型检查。应直接验证原值，再检查各项；公开验证函数也应针对异常类型独立测试。[D04]

### 3.3 评分：必须能在面试中准确写出

记 L 为模型llm_score，R为规则分，Q为证据质量分：

    Q = 0.6 × coverage + 0.4 × consistency

coverage和consistency来自模型；Q由后端计算，不信任模型自报的score。[D08]

    模型provider失败：Final = R
    没有有效证据：    Final = 0.6L + 0.4R
    有有效证据：      Final = 0.5L + 0.3Q + 0.2R

≥80为可信新闻，≥60为存疑信息，≥40为疑似谣言，其余为高风险谣言。[C13][C14]它是业务合成分，**不是“新闻为真的概率”，不是准确率，也未经概率校准**。[D05][C03]

另外两个分数不要混用：

- evidence_score是有效证据检索分均值×100，当前主链没有把它直接作为Final的30%项。
- 后端按来源、时效、提取置信度、重复度调整单条证据quality，再以0.55×relevance+0.45×adjusted_quality重排；这没有替换Final使用的Q。
- 文件末尾calculate_degraded_final_score中的旧公式不在当前主执行路径，不可拿它解释实际结果。[D05][R10]

规则分从100扣除夸张、无来源、情绪、绝对化、冲突等项。模型故障时只靠这些规则仍可能得到高分，因此“返回了结果”不等于“可靠降级”。缺少证据不足/无法判断的明确最终状态，是应优先修正的产品语义。[C03][D05]

### 3.4 后端与可靠性

已实现的工程能力包括Router/Service/CRUD分层、SQLAlchemy事务、Alembic迁移、JWT与数据库角色校验、输入schema、结构化日志/请求ID、报告补偿、缓存、Celery任务与健康检查。

需准确限定：

| 场景 | 已有措施 | 未闭环的问题 |
|---|---|---|
| Chroma客户端故障 | 清理缓存句柄后重试一次 | 不代表业务数据重试全链路有幂等保证 |
| 索引失败 | MySQL任务状态，默认3次尝试、线性延迟 | processing进程崩溃后缺租约回收；多实例缺原子抢占 |
| LLM仲裁错误 | 一次focused修复、显式失败状态 | 无通用HTTP退避重试；规则降级仍可能显示高可信 |
| 联网失败 | 返回空证据，继续本地路径 | 本地检索故障不会同样转网络 |
| 异步检测 | 先存任务、Celery执行、完成状态短路 | 前端未轮询；并发抢占/恰好一次未保证 |
| 报告生成 | UUID新文件→DB提交→清旧文件；失败删新文件 | commit后refresh失败会进入外层清理，存在已提交引用被删文件的窗口 |
| 超时 | fetch/Bocha/LLM各有局部timeout | 没有统一端到端deadline；前端检测120秒、Nginx上游60秒也需协调[F04] |
| 缓存 | Redis cache-aside、按Prompt/模型/契约等构key、TTL抖动 | 不等于已有命中率收益；没有同请求single-flight |
| 观测 | HTTP/DB/task/cache指标，OTel开关与span | LLM usage/token/cost缺失；部分阶段时间保存顺序有问题 |

来源：[Chroma][R13]、[索引任务][B03]、[异步任务][B06]、[worker][B07]、[报告提交][B05]、[观测][O01]、[缓存][O02]。

### 3.5 Security：有实质设计，但不要写“全面安全”

**认证/权限：** bcrypt保存密码，JWT默认HS256、有效期1440分钟；每次通过token取用户并查数据库active/role，管理员权限来自数据库，不直接信任JWT携带的角色。是普通用户/管理员两级控制，不是复杂RBAC策略引擎。[S01][S02][C01]

**限流：** 检测默认3次/60秒、按客户端IP；Redis Lua原子INCR/EXPIRE，无法使用且required时返回失败；可选模式有进程内锁保护的fallback。Redis窗口和内存滑窗语义不同，进程内计数不能保证多实例总限额。可信代理配置影响IP真实性。[S03]

**SSRF细节：**

1. 初始URL只允许HTTP/HTTPS；解析主机并移除fragment。
2. IP字面量直接检查；域名检查DNS解析出的全部IPv4/IPv6地址。
3. IPv4-mapped IPv6先转换，拒绝私网、回环、链路本地、多播、保留和未指定地址；任一解析结果危险就拒绝。
4. 禁用自动重定向，接管301/302/303/307/308，每跳检查主机，最多3次。
5. 默认请求timeout10秒、读取上限2MiB，限定文本/HTML类型。[S04]

**剩余边界：** DNS检查结果未固定到实际连接IP，存在检查与连接间的重新解析窗口；重定向后的URL没有每次统一调用初始scheme白名单校验。这是静态风险，未做利用验证。2MiB是读取上限，不是已证明超大响应会被明确拒绝；10秒也不是整个检测SLA。

**文件访问：** owner/admin权限、解析路径必须位于报告根目录、限定UUID报告文件名；Jinja模板开启autoescape。业务查询主要走SQLAlchemy绑定参数，不能据此宣称整个仓库“无SQL注入”。[S05][B04]

### 3.6 Testing：数量与覆盖都要讲清楚

静态AST统计backend/tests内71个文件、533个test_函数定义；evaluation/tests内11个文件、131个定义；告警适配器1个文件、3个定义，总计667个Python测试函数定义。**这不是667个实测通过案例，也不是覆盖率。**

有招聘价值的覆盖方向：

- LLM解析75个定义：缺字段、别名、JSON/文本容错、证据质量与仲裁约束。
- 联网53个：触发条件、候选规范化、强身份去重、候选ID、输入不变性。
- 检测API34个：入口、异常/状态、权限与集成行为。
- 网页抓取25个：HTML/结构化内容、正文识别、失败类别、地址风险与重定向。
- Embedding20个：provider输入、维度与响应边界。
- 报告service20个：临时SQLite/临时目录、生成/替换/清理、归属和路径。
- 知识同步15个、索引任务5个：数据库/向量失败和状态处理。
- 另有迁移、认证、限流、任务、缓存、图执行器、trace、v2检索和字段传播的测试。

测试利用unittest.mock替代LLM和网络；临时SQLite与目录减少外部依赖；API通过dependency override隔离数据库。Chroma真实集成测试存在但依赖不可用时可skip，不能把它当真实服务测试总是完成的证据。SQLite也不能覆盖全部MySQL事务/锁语义。[T01][T02][T03][T04]

前端20项是6个测试文件中的工具/代理层测试，不是19个页面都经过浏览器验证。没有可确认的正式浏览器E2E测试套件或覆盖率报告。

### 3.7 Evaluation：有框架，缺可信Benchmark

不能简单说“项目没有evaluation”。实际存在：

- run_evaluation直接调用detect_news_credibility。
- 分类与Hit@K、Recall@K、MRR指标计算，排除demo，延迟统计区分成功记录。
- seed、数据集hash、commit元数据与断点续跑结构。
- AI engineering gate及评测计算器测试。[V01][V02][V03]

但**目前最大的简历短板之一是缺少可信、无泄漏、可复现的真实Evaluation Benchmark**：

1. news_eval.csv共80条，为20主题×4标签；标题带“可信样本”等标签，正文直接提示期望输出，并嵌入核验依据。评测输入发生目标泄漏。
2. reviewer_2_provenance明确为“独立规则复核预标注（非真人）”，状态“待两名真人复核”；不能写成双人标注金标准。
3. 20条知识库样本与80条新闻高度主题对应，应做主题级划分，不能把同主题改写随机分开当泛化测试。
4. 当前树未见可用于复核的真实evaluation/output实验结果；不能据此写准确率、Recall提升、P95或成本节省。
5. AI gate的3条sample_cases是硬编码预测夹具，用于验证判分，不是实时调用模型得出的Benchmark。
6. runner把db_save记为report_latency；CSV适配器把success映射为accepted/ok，可能掩盖退化状态；指标语义也需要修正。[V04][V01][V03]

可写“实现端到端评测脚本与召回指标计算”。不可写“在80条金标准数据上达到XX准确率”“验证RAG显著提升”。

### 3.8 Docker/部署：配置丰富，可复现性仍需修复

仓库已有Docker、Redis、队列、CI、Tracing、监控配置，不能把这些列成“完全缺失”。真正问题是完整链路验证：

- compose构建上下文分别为./backend和./frontend；两个Dockerfile仅复制各自上下文。
- 共享contracts位于仓库根目录；后端loader用parents[3]寻找，前端相对import也指向根目录。
- 当前打包配置没有把根contracts带进镜像：前端构建解析、后端模块导入存在明确的缺文件路径问题。此结论来自路径分析，本轮没有实际构建镜像。[C05][C06][C07][C08][C09]
- 生产部署脚本有构建/启动/迁移/检查步骤[C15]，但不能证明部署曾成功；worker镜像更新、先up后迁移和回滚也需复核。
- k6阈值是验收目标；CI脚本主要压health/ready/metrics，不是模型检测吞吐。没有实测产物就不能写“P95＜500ms”。[C10][C11]

除明确文档/注释外，“为什么”是由实现推导的合理解释，**不是假定作者当时做过正式选型实验**。面试可以解释当前取舍，不能编造比较数据。

| 7. 何时联网 | 总联网、永不联网、按用户手动 | 0.45/0.60与有效数3的规则门限[R06] | 外部依赖可控，但相似度不是充分证据 | 分离raw cosine/fusion/rerank；用claim覆盖和独立域名扫参 |
| 8. 为什么URL normalization | 字符串完全比较、删除全部query | 去fragment、规范scheme/host/尾斜杠，保留path大小写和query[R07] | 去除部分同页差异；query参数仍可能产生重复 | 区分身份URL与展示URL；逐域处理追踪参数，避免误并内容 |
| 9. 为什么强制证据ID与契约 | 信任模型自由文本、仅JSON解析 | 候选集合约束+完整覆盖+互斥校验[D04][C08] | 输出可追踪、失败可判定；校验维护成本增加 | 统一schema与运行时validator；增加有限数值、原始类型校验 |
| 10. 为什么只修复仲裁一次 | 不重试、无限重试、全链重跑 | focused重试至多1次，仍失败显式状态[D11] | 调用次数有界；不能确保修复成功 | 分开网络/格式/语义错误；记录修复率、成本和总deadline |
| 11. 为什么JWT还查数据库 | 完全无状态JWT、服务端session | 验证token后读取active和role[S01][S02] | 角色/停用及时生效；每次增加DB读；缺token即时吊销机制 | 以实际威胁模型决定短token、refresh/revoke策略 |
| 12. 为什么知识写入要outbox | 同步写MySQL+Chroma、只写一个存储 | 知识和索引任务同事务，然后异步同步[B02][B03] | 缩小漏任务窗口；允许短暂索引滞后 | CAS/行锁抢占、lease回收、幂等版本键、积压/死信指标 |
| 13. 为什么报告先新文件再DB | 先记录后文件、直接覆盖旧文件 | 新UUID产物、提交引用、后清旧文件[B04][B05] | 大多数失败可保留旧版；无法覆盖进程崩溃与提交不确定 | 显式生成状态、提交边界、定时对账、故障注入测试 |
| 14. 为什么Alembic与安全抓取 | create_all临时建表、任意URL直接请求 | 11次线性迁移；抓取逐跳检查并限定资源[S04][C12] | schema演进可审计，减少网络访问风险；仍有部署顺序/DNS边界 | 干净库升级与回滚演练；固定目标IP并保留TLS主机校验 |

## 9. 30个最可能的项目面试问题

每题包含提问意图、代码位置、可用回答与现有边界。回答应以自己能复现的代码为准，不能背成已经完成改进。

### RAG（1—6）

**1. 本地证据少于3条就一定联网吗？**
- 为什么问：验证你是否真正读懂路由条件，而非背“RAG不足就搜索”。
- 位置：web_search_service.py:59。[R06]
- 应答：还要全局与请求允许；无候选、top1＜0.45，或top1＜0.60且≥0.30的候选少于3才触发；一条高分候选可以阻止联网。
- 潜在漏洞：高相关不代表充分支持或独立来源，需加入主张覆盖与可靠性信号。

**2. 为什么阈值是0.45和0.60？**
- 为什么问：检查是否有实验意识和分数语义。
- 位置：web_search_service.py:22；rag/contracts.py:71。[R06][R08]
- 应答：当前是配置规则，未证明最优；应在无泄漏相关性集上扫参并观察联网率、召回和成本。
- 潜在漏洞：v2以fusion分冒用similarity字段，不能直接复用cosine阈值。

**3. 为什么不是只做一次全文Embedding？**
- 为什么问：考察多断言、长文本与召回粒度。
- 位置：detection_service.py:1015；evidence_arbitration_quality.py:61。[R09][R10]
- 应答：规则提取最多5个主张，最多4query分别召回并RRF融合，尝试覆盖不同事实。
- 潜在漏洞：规则不是语义解析；多query也会引入噪声，需单/多query消融与claim级Recall。

**4. 你说的hybrid究竟是什么？**
- 为什么问：检查概念是否一致。
- 位置：knowledge_service.py:375；rag/retrieval.py:278。[R01][R02]
- 应答：v2内部是dense和SQL lexical融合；RAG_INDEX_VERSION=hybrid则表示v2空时回退v1，二者含义不同。
- 潜在漏洞：lexical不是BM25；v2缺MySQL回查，融合质量尚未实测。

**5. 700/100分块与父文档聚合解决什么？**
- 为什么问：考察chunk参数、上下文与引用身份。
- 位置：rag/chunker.py:37；retrieval.py:206。[R03][R02]
- 应答：按字符段落/滑窗提高局部召回，保留knowledge_id，最多2chunk/父文档，最终按父文档输出。
- 潜在漏洞：不是700token；叠加overlap可能超过700字符；文档聚合可能压掉其他有效片段。

**6. 你的MMR、reranker和压缩分别是什么？**
- 为什么问：防止算法名词包装。
- 位置：retrieval.py:249；reranker.py:121；contextual_compression.py:30。[R02][R05][R11]
- 应答：当前“MMR”实为来源罚分，reranker为规则；模型callback未接；片段提取是词项窗口，仍保留全文。
- 潜在漏洞：不能声称标准MMR、模型rerank或已节省token；先测失败案例再补算法。

### LLM（7—11）

**7. 为什么json_object之后还需要后端校验？**
- 为什么问：考察结构合法与业务合法的区别。
- 位置：llm_service.py:503；detection_service.py:143。[D07][D04]
- 应答：可解析JSON仍可能有未知候选、漏项、重复、错立场或越界分数；必须对实际候选集合验证。
- 潜在漏洞：现有手写validator原始类型校验有改进空间，json_object也非严格JSON Schema。

**8. candidate ID和中立顺序各有什么作用？**
- 为什么问：考察证据归属和顺序偏差。
- 位置：detection_service.py:125/430；web_search_service.py:208。[D04][R07]
- 应答：ID连接输入候选与仲裁结果；SHA256种子排序使顺序不直接等于检索优先级且可复现。
- 潜在漏洞：web ID只在本次调用唯一；脱敏只删顶层检索字段，嵌套分数仍可能影响模型。

**9. 为什么只重试一次仲裁而不重跑整个请求？**
- 为什么问：考察成本和故障分层。
- 位置：detection_service.py:466/510。[D11]
- 应答：检索已完成，错误集中在证据结构/语义；focused修复重用候选，限制额外调用次数。
- 潜在漏洞：这不是网络backoff；修复失败后清空有效证据，但其他模型结论仍可能被使用。

**10. 你的可信度分数是什么，怎么证明合理？**
- 为什么问：检查产品语义、公式与校准意识。
- 位置：detection_service.py:643；llm_service.py:1080。[D05][D08]
- 应答：它是条件加权业务分；有证据.5L+.3Q+.2R，无证据.6L+.4R，provider失败R；Q=.6coverage+.4consistency。
- 潜在漏洞：不是概率；后端证据质量调整未进入Final的Q；无证据与模型故障缺明确拒判语义。

**11. Prompt怎么管理、防注入、版本化？**
- 为什么问：检查模型行为治理是否落地。
- 位置：llm_service.py:273；prompt_output_contract.py:80；PromptTemplate模型。[D06][C08]
- 应答：主模板可管理和设默认，系统指令/转义/必需内容保护，统一契约追加；有契约版本。
- 潜在漏洞：缺Prompt不可变版本与实验回滚；转义不能根除注入，不能把contract_version等同完整Prompt版本。

### Backend（12—15）

**12. 为什么同步接口里已有Celery，页面还可能失败？**
- 为什么问：考察跨层契约。
- 位置：detect.py:92；DetectView.vue:459。[D02][F01]
- 应答：默认同步返回detection_id；异步创建任务返回202/task_id，但当前页面仍等待detection_id。
- 潜在漏洞：缺轮询、超时、取消/失败反馈；应完成接口与UI一起验证后再开启异步。

**13. 一个succeeded判断能保证任务幂等吗？**
- 为什么问：区分顺序重复与并发重复。
- 位置：detection_task_service.py:100。[B06]
- 应答：只能避免已完成后的重复；两个worker可同时读到未完成，检测保存与任务成功提交也有窗口。
- 潜在漏洞：缺CAS/锁、业务唯一键和租约；late ACK不等于exactly-once。

**14. 3次/60秒限流在多实例下成立吗？**
- 为什么问：检查原子性和代理IP。
- 位置：core/rate_limit.py:14；client_ip.py。[S03]
- 应答：Redis路径使用原子Lua计数可共享；内存fallback仅本进程。client IP还依赖受信任代理判断。
- 潜在漏洞：两种窗口语义不同；共享IP误伤，代理配置不当可能使配额失真。

**15. 30秒模型timeout能保证接口30秒内返回吗？**
- 为什么问：检查整链延迟预算。
- 位置：llm_service.py:503；web_content_fetcher.py:20；frontend API；nginx配置。[D07][S04][F02]
- 应答：不能，还包括检索、多query、搜索、可能的修复和保存；当前是阶段局部timeout。
- 潜在漏洞：缺总deadline；前端120秒与代理60秒需协调，不能把配置写成SLA。

### Database / Storage（16—19）

**16. 为什么MySQL与Chroma之间要索引任务表？**
- 为什么问：考察双写一致性。
- 位置：knowledge_service.py:287；knowledge_index_jobs.py:133。[B02][B03]
- 应答：知识和任务同事务提交，之后异步upsert向量并记录失败，避免知识提交后完全没有补建索引线索。
- 潜在漏洞：任务processing缺过期回收，多实例缺抢占；是最终一致性设计，非分布式事务。

**17. Chroma命中已删除知识怎么办？**
- 为什么问：检查索引是否被当作主数据。
- 位置：knowledge_service.py:375。[R01]
- 应答：v1逐条查MySQL，删除不存在的候选并用最新metadata；v2目前没有同样处理。
- 潜在漏洞：v2可能输出过期数据；需要统一父记录存在性/版本检查与索引对账。

**18. 先生成PDF再提交DB，失败能完全恢复吗？**
- 为什么问：考察文件和事务边界。
- 位置：report_service.py:193；report_crud.py:147。[B04][B05]
- 应答：新UUID文件避免覆盖旧版；失败删新文件，提交成功再删旧文件，属于补偿。
- 潜在漏洞：commit后refresh失败可能触发删除已引用文件；崩溃与清理失败需对账。

**19. 证据JSON和evidence_matches为什么同时存在？**
- 为什么问：考察查询结构与审计快照。
- 位置：detection_service.py:745/796；evidence_match.py。[D10]
- 应答：关系表便于关联展示，JSON保留候选、仲裁和质量状态快照。
- 潜在漏洞：目前关系表写入遗漏来源URL/类型/时间；两份数据要有明确版本和一致口径，报告引用未闭环。

### Security（20—23）

**20. JWT为什么还查用户数据库？**
- 为什么问：考察停用、权限变更与认证授权边界。
- 位置：core/deps.py:15/47；core/security.py。[S01][S02]
- 应答：token只证明身份声明，数据库决定当前用户是否active、是否admin。
- 潜在漏洞：没有完整token吊销/refresh流程；两级role不应称复杂RBAC引擎。

**21. 你的SSRF检查为什么要拿全部DNS地址？**
- 为什么问：检查IPv6、多A记录与映射地址。
- 位置：web_content_fetcher.py:225。[S04]
- 应答：域名可返回多个IPv4/IPv6，任一危险地址都拒绝；IPv4-mapped IPv6转换后检查。
- 潜在漏洞：校验IP未绑定后续连接，无法声称阻断DNS rebinding。

**22. 初始URL安全，为什么重定向还要校验？**
- 为什么问：检查公网跳内网与scheme边界。
- 位置：web_content_fetcher.py:209/395。[S04]
- 应答：禁自动跳转，最多3次并逐跳检查主机，避免只验证最初地址。
- 潜在漏洞：每跳没有统一重做scheme白名单；当前只是静态风险，尚无利用验证。

**23. 知道UUID任务ID或报告ID就能下载吗？**
- 为什么问：考察对象级授权。
- 位置：detection_task_service.py:69；report_service.py:364。[B06][S05]
- 应答：报告校验owner/admin及路径；注册用户任务校验归属，但匿名任务user_id为空时相当于UUID持有者可读。
- 潜在漏洞：UUID是难猜标识，不是身份；应明确访客任务是否可分享，必要时加会话或短期签名。

### Testing / Evaluation（24—27）

**24. 你说533个后端测试，实际通过多少？**
- 为什么问：检查指标诚实性。
- 位置：backend/tests与本报告测试日志。[T01]
- 应答：533是AST函数定义数；本轮后端受依赖阻塞未跑通。可确认前端20、告警3通过，评测套件有2个error。
- 潜在漏洞：不能把收集数量当通过数量，也不能用单元测试代替真实服务集成。

**25. SQLite和mock能发现哪些问题，漏哪些问题？**
- 为什么问：考察隔离与真实性取舍。
- 位置：test_report_service.py:33；test_web_content_fetcher.py:50；Chroma集成测试。[T02][T03][T04]
- 应答：快速复现解析、权限、失败清理；临时DB/目录隔离测试数据，mock控制网络错误。
- 潜在漏洞：漏MySQL锁/事务、真实provider响应漂移、DNS/连接语义与PDF环境依赖，需要分层集成测试。

**26. 80条数据为什么还不能叫gold benchmark？**
- 为什么问：检查泄漏和标注质量。
- 位置：evaluation/datasets/news_eval.csv首条及review字段。[V04]
- 应答：输入标题/正文含目标标签与核验依据，且第二reviewer非真人、待复核；要去目标提示、主题拆分、冻结并人工标注。
- 潜在漏洞：同主题四种改写不是独立真实新闻；清理后也不能沿用旧结果。

**27. Recall@K、Hit@K和MRR有什么不同？**
- 为什么问：检查是否真正理解评测脚本。
- 位置：evaluation/metrics.py:106/129。[V02]
- 应答：Hit看至少命中一个相关项；Recall看标注相关项覆盖比例；MRR看首个相关项倒数排名；必须有相关证据标注。
- 潜在漏洞：不完整gold会影响Recall；不能把向量高分或模型自己判断当独立真值。

### Architecture（28—30）

**28. 为什么这个项目不能直接叫自主Agent？**

**29. 为什么本地共享契约到Docker里就找不到？**

**30. 只投入一周，你会先加Agent框架还是补什么？**

### P2：按真实需求补

## 11. README重构与GitHub主页

### 11.1 README应按“让陌生人验证项目”的顺序写

1. **一句话定位与边界**：证据检索与受约束LLM分析；固定工作流，辅助核查，不宣称输出是真实概率。

4. **三项核心工程设计**：候选契约、任务化索引同步、报告补偿；链接具体实现/测试。

## 13. 技术负责人为什么应该让作者进入面试？

我会给面试机会，原因有具体代码支撑：

1. detection_service没有直接信任模型的证据列表，而是约束候选ID、完整覆盖、互斥关系与字段，失败时做一次局部修复。[D04][D11]
2. 检索不是取Top-K后机械拼Prompt：已有多主张查询、融合、父文档回收、本地不足补网，以及候选和有效证据的区分。[R09][R02][R06]
3. 作者尝试解决真实AI应用的多存储问题：知识与索引任务同事务、向量失败重试、报告新旧文件补偿。[B02][B03][B04]
4. 网络和文件访问有具体边界：DNS/IP分类、重定向检查、归属与路径校验，并有对应异常路径测试源码。[S04][S05][T02][T03]
5. 已经搭出评测、测试、观测结构，具备把工程问题转为可验证结果的基础，尽管现有Benchmark尚不可信。[V01][V02][O01]

这足以说明项目包含值得深入考察的AI应用工程问题。**面试邀请不等于认定作者已经掌握全部代码**：我会重点要求现场解释上述真实路径，修一个边界问题，并说明为什么现有阈值、评分和评测不能被夸大。若作者能做到，这个项目能够成为实习生简历中有分量的第一项目。
